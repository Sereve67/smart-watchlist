# Smart Watchlist

A market watchlist built around one idea: **the price is not the interesting
number, the change since you last looked is.** Two people watching the same
five tickers a week apart shouldn't both get "here are five prices" - the
person who checked yesterday should see almost nothing, and the person who
checked a month ago should see exactly which of their five names actually
did something worth their attention, and how much.

## Running it

Requires Node.js 18+.

```bash
cd server
npm install
npm start
```

Then open **http://localhost:8787**. Pick any username (no password - see
"Auth" below for why). The frontend is served by the same server, no
separate build step.

There's no external API key to configure: market data is simulated
in-process (see "Why simulated data" below), so it works fully offline and
produces the same interesting behaviors (volatility bursts, staleness,
source conflicts) deterministically enough to demo.

To see two "devices" sharing state, log in with the same username in a
second browser (or an incognito window) - the same watchlist and
last-seen snapshots show up there too.

## What "meaningfully changed" means here

The obvious version of this product shows raw % change and lets the user
eyeball it. That's actually two different failures depending on the stock:

- For a calm name (an index fund, a utility), a 1.5% move over a week is
  a big deal and gets buried in the noise of daily price flicker.
- For a genuinely volatile name, a 1.5% move is Tuesday, and a fixed
  "alert at 2%" threshold either fires constantly or misses the actual
  outlier days.

So significance is **volatility-adjusted**, not a flat threshold: the
system tracks each symbol's own recent realized volatility (stdev of
recent returns) and expresses the move-since-you-last-checked as a
z-score against that baseline. A z-score of 2+ means "this is an unusual
move *for this symbol*," which is a more honest definition of
"meaningful" than any single percentage could be for a watchlist that
might contain both SPY and a small-cap.

On top of the statistical signal, three deterministic triggers always
count regardless of volatility, because they're meaningful on their own
terms: crossing a 52-week high or low, and an unusual volume ratio versus
the symbol's average (interest/participation spiking, not just price).

Severity is bucketed (`notable` / `significant` / `major`) rather than
shown as a raw score, because a bucket is what a person scanning a list
of fifteen tickers can actually act on at a glance.

## What information is surfaced, and what isn't

Each row shows: price, today's change, the volatility-adjusted change
since your last visit, a short live trend line, and severity/context
badges (52-week high, volume spike, stale). Deliberately **not** shown by
default: full order-book depth, intraday OHLC candles, or a news feed -
those are legitimate features for a trading terminal, but they compete
for attention with the actual point of this product, which is "tell me
what changed," not "give me everything." A "reviewed" state
(click a row, or "mark all reviewed") explicitly separates *looking* at
the list from *acknowledging* it, so opening the app doesn't silently
erase the thing you opened it to see.

## How state persists across sessions and devices

There's a real backend and a real (if intentionally simple) datastore -
this is not a localStorage-only demo. Every watchlist item and every
"last seen" snapshot lives server-side, keyed by user id. Logging in with
the same username on a different device resolves to the same user id, so
the watchlist and every symbol's diff baseline are identical there. See
`server/src/store.js` for the persistence layer and `server/src/auth.js`
for how identity resolves (a deliberately minimal username-claim scheme -
see "Where I kept things simple" below).

The "since you last checked" diff is a genuine per-user, per-symbol
snapshot (price, volume, day range, 52-week range at the moment you last
acknowledged it) - not "since the page loaded" or "today's change," which
is what most watchlists actually show today.

## Handling stale, delayed, and conflicting data

The simulated feed intentionally misbehaves like a real one, and the
system is built to notice and say so rather than paper over it:

- **Two independent upstream sources per symbol** that usually agree
  closely but occasionally diverge (real vendors do this). Reconciliation
  policy: prefer the source that actually reported this tick; if both
  reported and disagree beyond a small tolerance, log the disagreement
  and deterministically prefer the primary rather than averaging (which
  would hide the disagreement) or dropping the tick (which would starve
  the UI). See `_logConflict` in `marketSim.js`.
- **Provider hiccups**: each source has a per-tick chance of silently not
  reporting. A symbol is flagged `stale` once neither source has updated
  it within a threshold window, and that's surfaced as a badge in the UI
  - the system never fabricates a fresh-looking price to paper over an
    outage.
- **Never trust "no data yet"**: a symbol just added to a watchlist has no
  baseline snapshot, and that's modeled explicitly as `isNew`, not as
  "0% change." A move can only be "significant" relative to something
  you'd actually seen before.

## How it scales

The core lever: **cost is O(distinct symbols being watched), not
O(users) or O(users × symbols).** A symbol only ticks while at least one
user anywhere is watching it (`marketSim.reconcile`, driven off the
store's `getAllWatchedSymbols()`), so 10,000 users all watching AAPL is
one simulated feed and one set of WebSocket fan-outs, not 10,000
redundant computations. Removing the last watcher of a symbol stops its
ticking; a periodic reconciliation sweep is the self-healing backstop
for any missed cleanup path rather than fragile manual
subscribe/unsubscribe reference-counting across two different subsystems
(REST handlers and WebSocket lifecycles) - that combination is a classic
source of leaks and double-counts, so the design avoids it entirely in
favor of "idempotently ensure this is on" plus "periodically reconcile
against the source of truth."

What's explicitly **not** built, and why that's fine at this scope: this
runs as a single process with in-memory simulator state and a JSON-file
store. That's the right call for a watchlist app being evaluated as a
prototype - it's simple, has zero external moving parts, and is easy to
read end-to-end. It is *not* the right call past a single instance. The
two swap points, if this needed to run on more than one server:

1. **Market state and pub/sub → Redis.** Right now tick fan-out happens
   via an in-process EventEmitter; a second server instance wouldn't see
   ticks computed on the first. Redis pub/sub (or a shared job that owns
   ticking and publishes) fixes that without touching the change-scoring
   logic at all - `marketSim.js`'s public shape (`ensureActive`,
   `getState`, `on('tick', ...)`) was kept narrow specifically so this is
   a localized swap.
2. **Durable data → Postgres.** Users/watchlists/snapshots are small,
   relational, and low-write-volume - a good fit for Postgres once you
   need multiple app servers reading/writing them concurrently. `store.js`
   exposes the same handful of functions a Postgres-backed version would,
   so this is also a one-file swap, not a rewrite.

## Where I kept things simple on purpose

- **Auth is a username claim, no password.** The brief is about the
  watchlist and change-detection system, not identity management. The
  cookie carries a stable user id and everything else is built against
  that id, so real auth (magic link, OAuth) is a drop-in replacement for
  `auth.js` alone.
- **No frontend framework.** The UI mostly reflects server-computed state
  (severity, diffs, staleness are all decided server-side); a build step
  and component framework would add ceremony without adding real
  interaction complexity yet. If this grew multi-pane layouts, drag
  reordering, etc., that calculus would flip.
- **JSON-file store, not a database engine.** Explained above - avoids a
  native dependency that might not build in a constrained sandbox, and
  the data volume/shape doesn't need one yet.
- **Simulated data, not a real market API.** No API key was available in
  this environment, and a simulator that can be told to misbehave
  (regime shifts, dropped ticks, source disagreement) is arguably more
  useful for demonstrating the resilience story than a live feed would
  be, since you can't force AAPL to gap 4% on demand for a demo. The
  simulator's shape mirrors what a real provider adapter would look like
  so swapping it is contained to `marketSim.js`.

## Project layout

```
server/
  src/
    index.js        # process entry, wiring, periodic reconcile sweep
    store.js         # persistence (users, watchlists, "last seen" snapshots)
    marketSim.js      # simulated market data feed, dual-source + staleness
    changeEngine.js   # "what counts as meaningful" scoring
    wsHub.js          # WebSocket fan-out of live ticks + live alerts
    routes.js         # REST API
    auth.js           # minimal cookie session
  data/db.json        # created on first run, gitignored
client/
  index.html
  app.js              # framework-free UI logic
  style.css
```

## Things I'd add next with more time

- Real provider adapter (Finnhub/Polygon) behind the same `marketSim`
  interface, with the two-source reconciliation applied to genuinely
  independent vendors instead of simulated ones.
- Per-user configurable significance sensitivity (some people want
  every `notable`, some only want `major`).
- Email/push digest for users who don't open the app for days, since the
  in-app banner only helps someone who actually returns.
